# 第五轮迭代需求文档

## 1. 迭代背景

当前项目核心代码已基本开发完成，主链路已覆盖：

- 内容采集
- Wiki 知识库提取与查看
- AI 写文
- AI 作图
- 选题分析与报告
- 账号空间
- 8 步内容生产管道

但在实际检查中发现，项目仍存在一批影响联调、验收和上线稳定性的关键问题。本轮迭代不再以新增大功能为目标，而是以“收口、对齐、稳定化、可验收”为核心目标。

---

## 2. 本轮迭代目标

第五轮迭代目标如下：

1. 修复当前已发现的结构性问题
2. 对齐代码实现、数据结构、接口契约与页面行为
3. 打通 MVP 核心主链路
4. 提升系统稳定性与可测试性
5. 为后续上线验收提供明确交付标准

---

## 3. 问题清单

### 3.1 数据结构与初始化问题

当前发现 `data/db.json` 中存在初始化结构不完整风险：

- 现有数据文件中重点可见 `keywords`、`articles`
- 首页依赖 `categories`
- 数据库代码默认结构还包含：
  - `categories`
  - `personas`
  - `styles`
  - `knowledgeBases`
  - `templates`
  - `apiConfigs`
  - `reports`

如果实际数据文件缺少这些根字段，可能导致：

- 首页分类为空
- 设置页异常
- 账号空间数据读取异常
- 报告、配置、模板等模块出现空值或边界错误

### 3.2 API 契约与代码不一致

当前 `docs/api-contract.md` 已经补充了 Wiki 和 AI 内容生成接口，但仍存在问题：

- 存在重复的 “AI 内容生成” 章节
- `POST /api/content/generate` 与 `POST /api/content/write` 存在能力重叠
- `POST /api/content/cover` 与 `POST /api/content/cover/prompts` 职责未完全收敛
- 平台搜索接口文档命名与实际代码路由存在差异

影响：

- 前后端联调成本高
- 文档无法作为唯一事实来源
- 后续测试与验收标准不稳定

### 3.3 核心主链路虽已开发，但缺完整验收

当前代码已具备以下能力：

- 分类管理
- 关键词管理
- 文章采集
- Wiki 提取
- Wiki 健康检查
- AI 写文
- 报告生成
- 管道执行

但尚未形成明确的“整链路验收标准”，导致：

- 无法判断当前是否达到可交付状态
- 关键边界问题可能被遗漏
- 页面联动、接口返回、异常处理未统一验证

### 3.4 Pipeline 持久化不足

当前 8 步 Agent 管道状态主要保存在内存中，存在以下问题：

- 服务重启后任务状态丢失
- 无法追踪历史执行记录
- 不利于长任务、异步任务和失败恢复
- 不适合正式环境的稳定运行

### 3.5 测试覆盖不足

当前已有部分单元测试，但仍缺少以下能力：

- API 集成测试
- 页面主链路测试
- Wiki 主流程测试
- 内容生成流式输出测试
- 关键交互 E2E 测试

影响：

- 回归风险高
- 每次迭代后稳定性无法量化
- Human Checkpoint 缺少可靠依据

### 3.6 环境配置与运行依赖不透明

当前项目依赖以下外部配置：

- AI API 默认配置
- XHS 平台 API Key
- WX 平台 API Key
- 内容生成模型参数

当前问题：

- 必填环境项未形成统一清单
- 缺少启动前自检机制
- 未配置时的错误提示不完全统一

---

## 4. 第五轮迭代范围

### 4.1 P0 必做项

#### P0-1 数据结构对齐与初始化补全

目标：

- 对齐 `data/db.json` 与 `src/lib/db.ts` / `src/lib/types.ts`
- 补全缺失的根字段
- 提供最小可运行的初始化数据

要求：

- `db.json` 至少包含以下根字段：
  - `keywords`
  - `articles`
  - `categories`
  - `personas`
  - `styles`
  - `knowledgeBases`
  - `templates`
  - `apiConfigs`
  - `reports`
- 提供至少 1 条分类数据，保证首页可正常进入业务流
- 缺失字段时后端应具备兜底兼容能力

验收标准：

- 首页可正常拉取分类
- 监控设置页不报错
- 账号空间页可正常读取空数据或默认数据
- 不因缺字段导致接口 500

#### P0-2 API 契约收口

目标：

- 让接口文档与当前代码实现一致
- 删除重复、冲突和历史遗留描述

要求：

- 合并重复的 “AI 内容生成” 章节
- 明确 `generate` 与 `write` 的职责
- 明确 `cover` 与 `cover/prompts` 的职责
- 对齐平台搜索接口命名
- 统一错误返回格式

验收标准：

- `docs/api-contract.md` 无重复章节
- 所有现有路由都有明确契约说明
- 前端联调时不再依赖猜测接口行为

#### P0-3 主链路验收标准建立

目标：

建立统一的 MVP 主链路验收流程。

主链路：

1. 创建分类
2. 创建关键词
3. 采集文章
4. 查看文章列表
5. 提取文章到 Wiki
6. 查看 Wiki 索引与日志
7. 执行 Wiki 健康检查
8. 生成选题报告
9. 基于 Wiki 生成正文
10. 生成标题与封面 Prompt

验收标准：

- 每一步均可成功执行
- 失败时有明确提示
- 页面状态与接口返回一致
- 无关键阻塞错误

### 4.2 P1 重要项

#### P1-1 Pipeline 持久化改造

目标：

- 将内存态任务状态改为可恢复的持久化结构

要求：

- pipeline 执行状态可查询
- 服务重启后历史任务不丢失
- 至少支持：
  - 任务 ID
  - 当前步骤
  - 执行状态
  - 执行历史
  - 错误信息
  - 开始时间 / 更新时间

验收标准：

- 执行管道后可通过 ID 查询状态
- 重启服务后任务记录仍存在
- 失败任务可追踪失败步骤

#### P1-2 错误结构统一

目标：

统一所有接口的错误返回格式。

要求：

- 统一成功格式
- 统一失败格式
- 避免部分接口返回 `msg`，部分接口返回 `error` 的混用

建议格式：

```json
{
  "code": 400,
  "error": {
    "name": "BAD_REQUEST",
    "message": "缺少必要参数"
  }
}
```

验收标准：

- 同类错误在不同接口中的字段结构一致
- 前端可以复用统一错误处理逻辑

#### P1-3 环境配置校验与错误提示优化

目标：

在运行前识别关键环境缺失问题。

要求：

- 梳理 AI、平台采集所需配置项
- 缺失配置时返回清晰错误
- 页面提示用户应该去哪里配置

验收标准：

- 缺少 API 配置时不会出现模糊报错
- 用户能明确知道需要配置哪一项

### 4.3 P2 增强项

#### P2-1 API 集成测试补齐

重点覆盖：

- categories
- keywords
- articles
- wiki ingest
- wiki index
- wiki lint
- report generate
- content generate

#### P2-2 E2E 测试补齐

至少覆盖：

- 首页进入
- 分类切换
- 文章提取到 Wiki
- Wiki 页面查看
- 报告生成
- AI 写文主链路

#### P2-3 页面空态与异常态统一

目标：

- 对无分类、无文章、无 API 配置、无 Wiki 数据等场景统一空态体验

---

## 5. 非目标

本轮迭代不重点处理以下内容：

- 新平台大规模接入
- 高级数据分析大屏
- 复杂权限系统
- 导出与分享
- 自动发布全链路
- 大范围 UI 重构

---

## 6. 交付物

本轮迭代完成后，应交付以下内容：

1. 对齐后的数据结构
2. 收口后的 API 契约文档
3. 主链路验收清单
4. Pipeline 持久化方案与实现
5. 关键 API 集成测试
6. 关键页面 E2E 测试
7. 已知风险与未完成项说明

---

## 7. 验收标准

满足以下条件，本轮迭代才可视为完成：

- `db.json` 与数据模型结构一致
- 首页可基于分类正常工作
- Wiki、报告、写文主链路可完整跑通
- API 契约与代码实现一致
- 关键接口错误结构统一
- 至少具备关键 API 集成测试
- 至少具备关键主链路 E2E 测试
- Pipeline 状态具备持久化或可恢复能力
- 已知风险已明确列出

---

## 8. 建议优先级顺序

1. 数据结构补全
2. API 契约收口
3. 主链路验收跑通
4. 错误结构统一
5. Pipeline 持久化
6. 集成测试补齐
7. E2E 补齐

---

## 9. 一句话定义本轮迭代

第五轮迭代的核心目标不是“继续堆功能”，而是：

**把已经开发出的能力真正收口成可联调、可验收、可稳定运行的一版系统。**
